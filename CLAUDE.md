# Git workflow — read before creating branches or committing

- **`main` is the single source of truth.** It's what's actually deployed to production. Never commit directly to `main` — always work on a branch and open a PR back into it.
- **`co-test` is an optional sandbox, not a required gate.** It's a separately deployed app (own Dockerfile, own DB, own Railway service) used for prototyping risky or unproven changes. Most work does NOT need to go through it — a well-understood fix or feature should branch straight off `main` and PR straight back.
- **Never merge `co-test` into `main` wholesale, and never merge `main` into `co-test` expecting it to "sync."** They are allowed to diverge structurally (different files, different function signatures, different architecture in the same-named file) and have done so for months. A batch merge between them WILL produce a large, likely-unresolvable set of conflicts — this already happened once (PR #21, open ~5 weeks, closed unmerged in favor of the pattern below).
- **The only way code moves from `co-test` to `main`: one small, scoped port at a time.** Branch off current `main` (name it `feature/prod-<thing>` or `fix/prod-<thing>`), manually bring over just that one proven change, verify it against `main`'s REAL current code (not `co-test`'s copy — see below), typecheck, PR, merge, delete the branch. See recent examples: PRs #22–#29.
- **Before porting anything from `co-test`, read `main`'s actual current file** (`git show main:path/to/file`) rather than assuming `co-test`'s local copy of that same-named file reflects what's really on `main`. This has caused a real incident before (a port was nearly merged based on a diverged `co-test` copy that didn't match `main` at all — missing files, different architecture). The `co-test-sync-reviewer` subagent (`.claude/agents/co-test-sync-reviewer.md`) exists specifically to do this check — use it before porting, or when asked "does this co-test change need to go to prod."
- **Keep the branch count minimal.** Only `main` and `co-test` are meant to be long-lived. (`features/frontend-setup` and `features/backend-setup` were retired 2026-08-17 — they were identical to `main` with no active workflow using them.) Everything else (`feature/prod-*`, `fix/prod-*`) is short-lived — delete it once merged.
